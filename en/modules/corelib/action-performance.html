Action Pipeline Performance ​

This page is the performance stance of the Emaki action pipeline: statically provable architectural advantages, a reproducible benchmark method, and the results table. This environment has no Paper/Folia server, so every quantified cell is marked "not run" with a closing condition — architecture claims are backed by source code, but numbers must come from a real server before they may be cited externally

Architectural advantages (source-verifiable) ​

1. Compiled once, zero parsing at runtime ​

A pipeline is compiled exactly once at config load through PipelineParser + StaticValidator into a CompiledPipeline (AST + type-checked arguments). At runtime ActionInterpreter executes that structure directly:

  • no re-tokenization, no argument type checks, no unknown-stage lookups;
  • argument rendering only runs render for values containing placeholders; pure literals are skipped;
  • compile failures are reported in full at load time (48+ rules), so there is no "found out at runtime" path for a wrong stage name

2. Gate short-circuiting and domain grouping ​

  • Gate short-circuit: a source returning Empty or a gate returning Halted enters a terminal state (stopped) immediately; all later stages are skipped with no cross-domain dispatch
  • Same-domain batching: StageGroup folds consecutive same-domain stages into one dispatch (foldable stages attach to the previous group), reducing Paper/Folia thread hops — e.g. two CONTEXT_ENTITY stages ("edit inventory" + "set XP") cause a single owner-thread transfer
  • Five-domain classification: SERVER_GLOBAL / CONTEXT_ENTITY / LOCATION_REGION / ASYNC_COMPUTE / UNDECLARED are mandatory at registration (StageRegistry.checkDomain); StageDispatcher routes by domain at runtime. Competitors generally have no domain classification, which is Emaki's structural difference on Folia

3. Zero-allocation observation on hot paths ​

The default StepReporter is NOOP (empty interface methods), so in non-debug runs every observation point is an empty call; ActionAuditLogger returns early when there is no DebugLogger. The observation layer adds no allocation or branching to production hot paths

4. Elimination before execution ​

Every gate's in/out counts are reported on StepReporter.gate (rendered as a funnel in dry-run/debug mode); semantically "filter first, act later" — filter/where eliminate unqualified targets before any action runs, avoiding cross-domain dispatches for invalid targets

Comparison stance against competitors ​

  • Statically citable (source-level facts): five-domain thread grouping with mandatory Folia domain declarations (MythicMobs/Skript have no such mechanism); 48+ compile-time diagnostics (MythicMobs relies on runtime errors + guessing from the Wiki)
  • Not citable: any throughput, latency, or TPS number. Competitor figures are marketing claims too; re-check the source date before quoting them externally
