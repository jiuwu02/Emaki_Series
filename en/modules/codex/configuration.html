Configuration ​

Every field in the EmakiCodex configuration files is listed below with its default value and purpose

EmakiCodex configuration is split into main settings, vanilla advancement pages, category entries, a GUI template, and language files. The four files detailed below are config.yml, codex/*.yml, gui/codex_gui.yml, and lang/*.yml -- keep their roles apart first:

  • config.yml: global switches, default resource release, vanilla advancement registration, and the PacketEvents coordinate channel
  • codex/*.yml: categories, entries, unlock conditions, and rewards; its category_id namespace is independent from advancements/*.yml page_id
  • gui/codex_gui.yml: category-entry GUI layout and placeholders
  • lang/*.yml: command, GUI, and console messages

The page and node fields of advancements/*.yml are documented in Advancements, category entries in Category GUI, and both automatic unlock paths in Triggers

config.yml ​

Default main configuration:

yaml
version: "2.0.0"
language: "zh_CN"
release_default_data: true
op_bypass: false

advancement:
  enabled: true
  announce_default: false
  remove_on_disable: true
  packet_coordinates: true
  triggers_enabled: true

Field reference (Required = No means the source supplies a default and the key may be omitted):

FieldTypeRequiredDefaultAllowed valuesDescription
versionstringNo2.0.0any stringConfiguration-structure marker; the internal migration constant is 1.0.14 and is not a release coordinate
languagestringNozh_CNfile name of lang/<language>.ymlUses lang/<language>.yml; falls back to zh_CN when blank or missing
release_default_databooleanNotruetrue / falseWhen true and the files are missing, releases the bundled defaults: advancements/example_page.yml, example_combat_page.yml, example_collection_page.yml, codex/example_category.yml, example_combat.yml, example_life.yml, plus the editor templates gui/editor_browser_gui.yml and gui/editor_page_gui.yml
op_bypassbooleanNofalsetrue / falseWhen true, OPs bypass the command permission checks; when false, they still need the relevant permission nodes
advancement.enabledbooleanNotruetrue / falseMaster switch for vanilla advancement registration; when disabled, loading and registration are skipped and /codex reload removes the plugin's registered nodes
advancement.announce_defaultbooleanNofalsetrue / falseDefault broadcast behavior when a node does not define announce
advancement.remove_on_disablebooleanNotruetrue / falseRemoves registered dynamic advancements when the plugin is disabled. The /codex reload rebuild always clears the plugin namespace before registering, regardless of this switch
advancement.packet_coordinatesbooleanNotruetrue / falseInjects node x / y into the client tree when PacketEvents is installed. The value is read when the packet gateway is built at enable time; changing it at runtime requires a restart
advancement.triggers_enabledbooleanNotruetrue / falseEnables automatic gameplay-trigger grants (node triggers.entries and entry unlock.triggers). When disabled, commands, API, and CoreLib actions can still grant manually

Configuration example (disable automatic triggers, keep coordinate injection):

yaml
language: "en_US"
op_bypass: true

advancement:
  enabled: true
  packet_coordinates: true
  triggers_enabled: false

Category files: codex/*.yml ​

Each file defines one GUI category. The filename is not the id; the category id comes from category_id. The composite entry id is always <category_id>/<entry_id>, for example example/first_blood

Shipped default excerpt (from codex/example_category.yml):

yaml
category_id: "example"
title: "<gold>Trial Codex</gold>"
icon: "minecraft-book"
order: 100

entries:
  first_blood:
    title: "<yellow>First Hunt</yellow>"
    description: "<gray>Defeat any hostile creature.</gray>"
    icon: "minecraft-iron_sword"
    hidden: false
    unlock:
      triggers:
        - event: "entity_kill"
      advancements: []
    rewards:
      attributes:
        physical_attack: 2.0
      actions:
        - "send_message text=<green>You claimed the first-hunt reward.</green>"

Field reference (every key below is available under each entry in entries):

FieldTypeRequiredDefaultAllowed valuesDescription
category_idstringNoemptynon-blank string (normalized to an id)Category id; the whole file is skipped when blank
titleMiniMessage stringNocategory_idMiniMessageCategory title used by the GUI tab
iconItemSource stringNominecraft-bookCoreLib ItemSource shorthandCategory icon
orderintegerNo100integerCategory-tab sort weight, ascending; ties are broken by category_id
entriesmapNoemptykeys are local entry idsEntry definitions
entries.<id>.titleMiniMessage stringNoentry idMiniMessageEntry title
entries.<id>.descriptionMiniMessage stringNoemptyMiniMessageEntry description
entries.<id>.iconItemSource stringNominecraft-bookCoreLib ItemSource shorthandEntry icon; a locked entry renders with the locked icon instead
entries.<id>.hiddenbooleanNofalsetrue / falseWhether to hide an entry while locked; false displays an unknown entry
entries.<id>.unlock.triggerslistNoemptytrigger listShared event triggers, see Triggers
entries.<id>.unlock.triggers[].eventstringYes—CoreLib event IDTrigger event ID (normalized); a blank value skips that entry
entries.<id>.unlock.triggers[].conditionCoreLib condition groupNoemptycondition.type + condition.entriesOptional; omitting it means the event itself is enough
entries.<id>.unlock.advancementslist<string>Noemptyvanilla advancement keyAny match unlocks the entry; values are trimmed and de-duplicated
entries.<id>.rewards.attributesmap<string,double>Noemptyattribute id → double (not 0.0)Contributes live after activation and is not snapshotted in player data; entries whose value is 0.0 are dropped, and duplicates are summed
entries.<id>.rewards.actionslist<string>NoemptyCoreLib action lineCoreLib action lines executed once on claim; the claimed state is stored before the lines run

Keep the unlock logic in one sentence: unlock.triggers and unlock.advancements are parallel paths, and either one can move an entry to the unlocked state. Unlocking, activating, and claiming are three separate steps: unlock does not auto-activate, and activation does not run the one-time claim actions

Usage example (two entries, unlocked through a trigger and an advancement):

yaml
category_id: "example"
title: "<gold>Trial Codex</gold>"
icon: "minecraft-book"
order: 100

entries:
  first_blood:
    title: "<yellow>First Hunt</yellow>"
    description: "<gray>Defeat any hostile creature.</gray>"
    icon: "minecraft-iron_sword"
    hidden: false
    unlock:
      triggers:
        - event: "entity_kill"
    rewards:
      attributes:
        physical_attack: 2.0
      actions:
        - "send_message text=<green>You claimed the first-hunt reward.</green>"

  master_miner:
    title: "<aqua>Deep Miner</aqua>"
    icon: "minecraft-diamond_pickaxe"
    hidden: true
    unlock:
      triggers:
        - event: "block_break"
          condition:
            type: "all_of"
            entries:
              - '%block_type% == "DIAMOND_ORE"'
      advancements:
        - "emakicodex:example/first_step"
    rewards:
      attributes:
        max_health: 5.0

Language files ​

Language files live in lang/*.yml. The default includes:

yaml
version: "2.0.0"
general:
  prefix: "<gray>[ <gradient:#D946EF:#F59E0B>EmakiCodex</gradient> ]</gray>"
  no_permission: "<red>You do not have permission to do that.</red>"

command:
  help:
    commands:
      reload: "Reload config, re-register advancements, resync all"
      grant: "Grant an advancement to a player"
      revoke: "Revoke an advancement from a player"
      debug: "Manage debug mode"

Language text supports MiniMessage (a tag-based format for colors and styles). Run /codex reload after editing to apply it

After editing config.yml, advancements/*.yml, codex/*.yml, gui/codex_gui.yml, or lang/*.yml, run /codex reload to apply the changes. Player files under data/<uuid>.yml are preserved by reload, so you can reload without worry
