EmakiCodex ​

EmakiCodex contains two independent codex models. advancements/*.yml defines and registers vanilla advancement pages and nodes, while codex/*.yml defines categories, entries, unlock conditions, and rewards for a separate category-entry GUI. The two models can be linked through advancement unlocks, but page_id and category_id are not interchangeable.

When PacketEvents is installed, EmakiCodex can inject configured node coordinates into the client advancement tree and re-push the registered tree to online players. Without PacketEvents, vanilla advancements still register normally, but node placement is handled by the vanilla client parent tree and online players may need to reconnect after a reload to see the updated tree. The category-entry GUI does not require PacketEvents; its action rewards still run through CoreLib, while attribute rewards are derived from the current configuration.

Core features ​

  • Vanilla advancement codex: each advancements/*.yml file is one vanilla advancement tab, with node keys like emakicodex:<page>/<node>.
  • Category-entry codex: each codex/*.yml file defines one GUI category; composite entry ids use <category_id>/<entry_id>, ordered by order.
  • Four entry states: entries move through locked, unlocked, activated, and claimed; activation and claiming are separate operations.
  • Two unlock paths: unlock.triggers listens to shared events, while unlock.advancements listens to vanilla advancements; either path can unlock an entry.
  • Two reward paths: rewards.attributes contributes live attributes after activation, while rewards.actions runs once when the player claims the reward.
  • Manual grant/revoke and admin entry control: administrators use /codex grant and /codex revoke for vanilla nodes, and admin unlock/reset for category entries.
  • Action grants and announcements: CoreLib exposes five advancement operations plus codex_show_toast and codex_broadcast_achievement.
  • Gameplay triggers: vanilla nodes use triggers.entries; category entries use unlock.triggers with shared gameplay events and conditions.
  • Completion and claim actions: vanilla completion runs actions.complete; category claims run rewards.actions.
  • PacketEvents coordinate channel: when PacketEvents is installed and advancement.packet_coordinates is enabled, vanilla node x / y values are sent to the client advancement screen.

Quick start ​

  1. Put EmakiCoreLib-*.jar and EmakiCodex-*.jar into the server plugins/ directory.
  2. Do not put emaki-codex-api-*.jar into plugins/; the API Jar is only for developer compile dependencies.
  3. After first startup, inspect plugins/EmakiCodex/advancements/example_page.yml.
  4. After editing or adding pages, run:
text
/codex reload
  1. Open the category-entry codex GUI:
text
/codex codex
  1. Grant the sample vanilla node for testing:
text
/codex grant Steve example/first_step
  1. Manage a category entry with its composite id:
text
/codex admin unlock Steve example/first_blood
/codex admin reset Steve example/first_blood

The full key form also works:

text
/codex grant Steve emakicodex:example/first_step

Two configuration models at a glance ​

One advancements/*.yml file defines one vanilla advancement page:

  • Page level: page_id (the key path prefix), title, background, root.
  • Node level: icon, title, description, frame, parent, x / y, toast, announce, hidden.
  • Node completion actions go in actions.complete, and gameplay triggers go in triggers.entries.

One codex/*.yml file defines one category-entry page:

  • Category level: category_id, title, icon, order, entries.
  • Entry level: title, description, icon, hidden, unlock.triggers, unlock.advancements, rewards.attributes, and rewards.actions.
  • Commands, GUI state, and data files use the composite id <category_id>/<entry_id>.

Both trigger systems use CoreLib condition groups with condition.type and condition.entries. Vanilla nodes register as emakicodex:<page_id>/<node_id>. See Advancements and Category GUI for the full field tables and interaction rules.

Notes ​

  • Vanilla advancements and the category-entry GUI keep separate state; do not use advancements/<page_id> where codex/<category_id> is required.
  • Vanilla nodes are completed through Codex grants: commands, actions, the public API, or triggers award the internal codex criterion.
  • actions.complete runs only on first vanilla completion; category rewards.actions runs only on the one-time claim.
  • Category rewards.attributes are not stored as numbers; they are derived from current configuration, so changing the reward config affects already activated players.
  • If advancement coordinates are enabled, configure x / y for every node in a page to avoid mixing explicit coordinates with client auto-layout.
