Skill Definitions ​

Skill definition files spell out what each field means, its default, and which values it accepts. Skill files live in plugins/EmakiSkills/skills/*.yml. One skill per file: you only describe what the skill is (name, cooldown, costs, upgrades) and hand the actual effect to the native script system or MythicMobs. Local resource definitions live in plugins/EmakiSkills/resources/*.yml

Loading rules ​

  • One file loads exactly one skill. A blank id makes the whole file be skipped and recorded as a loader issue
  • To park a skill temporarily, set enabled: false; it never enters the registry, which is the same as the skill not existing
  • Skill ids are normalized to lower case; ids inside list fields get the same treatment, with - folded to _
  • List fields accept alias keys (see the table); when both are present their entries are merged in order and de-duplicated

The condition block ​

Casting and upgrading share the same condition block. The condition text is rendered through PlaceholderAPI before evaluation

yaml
condition:
  type: "all_of"
  entries:
    - "%player_level% >= 5"
    - "%emakiskills_level_fireball% >= 2"
FieldTypeRequiredDefaultValuesDescription
conditionmapNonone—Must be a mapping node; without entries the block counts as no condition at all
condition.typestringNoall_ofall_of, any_of, none_of, at_least, exactlyHow multiple conditions combine
condition.entrieslist<\string>No[]Expression stringsCondition expressions; omitting the key leaves the whole block empty
condition.required_countintegerNo0≥ 0Match threshold for the at_least / exactly combine modes
condition.invalid_as_failurebooleanNotruetrue / falseRead by the shared condition parser; EmakiSkills' cast and upgrade paths always treat an unparseable expression as "not passed"
condition.on_pass.actions / condition.on_fail.actionslist<\string>No[]—Read by the shared condition parser; EmakiSkills skills do not use them
condition.on_fail.block_output / condition.on_fail.messageboolean / stringNofalse / ""—Same as above; not used by EmakiSkills skills

An unparseable condition counts as "not passed": the skill is not cast and the upgrade is rejected. The cast failure key is cast.condition_not_met and the upgrade failure key is upgrade.condition_not_met

Condition text is handed to PlaceholderAPI before evaluation, so every %...% in it must be resolvable by an installed expansion (for example %emakiskills_level_fireball%). An unresolvable placeholder reaches the expression as-is and, per the rule above, counts as not passed

Variables and scripts ​

  • variables: runtime values; syntax and types are in Variable types. Script lines, conditions, and text read them as %var.<name>%
  • script: the native script block; keys and phases are in Native scripting
yaml
variables:
  fire_damage:
    type: expression
    value: "10 + %level% * 5"
  battle_cry:
    type: random_text
    lines:
      - "<red>Burn!"
      - "<red>Flame power!"

script:
  mode: native          # native / mythic / hybrid
  stop_on_failure: true
  actions:
    cast:
      - 'trigger | damage amount=%var.fire_damage%'
    hit:
      - 'trigger | ignite duration=3s'

resource_costs ​

resource_costs:
  - type: "ea-resource"
    target_id: "mana"
    amount: 20
    operation: "consume"
    failure_message: "<red>Not enough mana."
FieldTypeRequiredDefaultValuesDescription
typestringYes—ea-resource, attribute-check (alias ea-attribute-check), local-resource, auraskills-mana (aliases aura-skills-mana, aura-mana), mythiclib-mana (aliases mmocore-mana, mythic-mana)Resource type. An unrecognized value makes the whole entry be dropped
target_idstringNo""Resource / attribute idThe local resource, Attribute resource, or attribute id involved
amountdoubleNo0≥ 0, negatives become 0Amount to check or deduct
operationstringNoconsumeconsume (deduct), require (check only)Any other value is treated as consume

Local resources versus other resource systems

Local resources are stored only in skill data and are not synchronized with EmakiAttribute. If you already keep a resource of the same name in EmakiAttribute, switch skill costs to ea-resource so the two never diverge

Upgrade configuration ​

yaml
upgrade:
  enabled: true
  max_level: 5
  gui_template: "upgrade_gui"
  failure_penalty: "none"
  economy:
    enabled: true
    currencies:
      - provider: "vault"
        currency_id: ""
        base_cost: 1200
        cost_formula: "%base_cost% * %target_level%"
        display_name: "<gold>Coins</gold>"
  success_rates:
    2: 100.0
    3: 90.0
  levels:
    2:
      materials:
        - item_sources:
            - "minecraft-blaze_powder"

      actions:
        success:

Upgrade flow and GUI ​

  • Compute the target level first (current level + 1), then clamp it by max_level; the skill must be unlocked and upgrade.enabled must be true
  • Order: condition check → SkillPreUpgradeEvent (cancellable, success rate may be replaced) → cost check → charge → roll → apply the level or the failure penalty
  • Costs are charged before the roll, so a failed roll does not refund the currency and materials already charged (compensation is only attempted when the commit stage throws)
  • Player-visible feedback comes from the upgrade.* keys in lang/<language>.yml (for example upgrade.success, upgrade.failed, upgrade.insufficient_funds)

The upgrade GUI is rendered from the template named by upgrade.gui_template; the type you write on each slot decides its content:

Slot typeContent
skill_displaySkill icon and name, with level, success rate, and failure-penalty text as replacements
cost_currencyCurrency cost list; shows gui.upgrade_cost_free when there is no cost. Replacements %currencies%, %currency_count%
cost_materialMaterial cost list, one line per item showing "have/required" and colored by whether it is satisfied. Replacements %materials%, %material_count%, %missing_count%
success_rateSuccess-rate title, replacement %success_rate%
confirmConfirmation button; its icon and status text switch between upgrades-disabled, max-level, insufficient-materials, and ready. Clicking calls the same upgrade service as the command

The GUI and the upgrade flow share one quote function (preview), so the numbers you see always match what gets charged: the GUI renders costs from the state at render time, and clicking Upgrade re-quotes and charges from that result. The numbers agree while the player's state is unchanged; if the state moved in between (a material was consumed elsewhere, for example), the re-quote and actual charge win, and a shortfall fails the whole attempt without charging

Skill sources and tag limits in config.yml ​

You write both blocks below in plugins/EmakiSkills/config.yml; they control how skills are recognized and how many can be equipped

Equipment skill source switches ​

yaml
skill_sources:
  read_lore_skills: true
  read_pdc_skills: true
  require_lore_pdc_match: false
FieldTypeRequiredDefaultValuesDescription
skill_sources.read_lore_skillsbooleanNotruetrue / falseWhether to read skills from equipment lore
skill_sources.read_pdc_skillsbooleanNotruetrue / falseWhether to read skills from equipment PDC
skill_sources.require_lore_pdc_matchbooleanNofalsetrue / falseStrict mode. When enabled, only the lore∩PDC intersection for the same item and slot is kept; skills present on just one side do not apply

Keep this in mind: the config precheck warns when both sides are off, or when strict mode is on with only one side enabled

Tag equip limits ​

When a skill's tags match an entry here, you can equip at most that many skills carrying the tag:

yaml
skill_tags:
  equip_limits:
    ultimate: 1
    mobility: 2
FieldTypeRequiredDefaultValuesDescription
skill_tags.equip_limits.<tag>integerNonone (unlimited)> 0; <= 0 or non-integer values ignore the keyMaximum number of skills with that tag equipped at once. Tag names are id-normalized with - turned into _
tag_limitsmapNononeSame as aboveLegacy key. Read as a fallback when skill_tags.equip_limits is empty

With the config above, at most one ultimate skill and two mobility skills can be equipped at the same time. Tags not listed here are unlimited
