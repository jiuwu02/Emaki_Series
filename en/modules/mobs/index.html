EmakiMobs ​

EmakiMobs is the custom mob system module. It lets server administrators define custom mobs with YAML, configure spawn rules, loot tables, and skill behaviors, with deep integration into EmakiAttribute, EmakiSkills, and EmakiItem.

Core capabilities ​

CapabilityDescription
Custom mob definitionsYAML-driven mob type, stats, appearance, and behavior; hot-reloaded.
Type overrideWhen id matches a vanilla EntityType name, the config is applied to all naturally spawned entities of that type.
Two spawn strategiesnatural intercepts vanilla spawn events; autonomous runs on its own scheduler (interval / player_follow / day_interval / cron triggers).
Loot table systemMulti-pool, weighted entries with count functions and looting enchant bonus.
EmakiItem integrationLoot table entries drop EmakiItem items through the emaki_item key.
EmakiAttribute integrationThe ea_attributes section feeds EA contribution providers for mob attributes; health/mana-style RESOURCE attributes do not work on mobs.
Skill triggersEleven trigger kinds (including five health-threshold tiers) fire CoreLib action pipelines.
Target selectorsA mob definition points target_selector at target_selectors.yml to filter and score targets; EmakiMobs also registers a type: emakimobs identity with CoreLib's target selector so the select source can recognise managed mobs.
Threat tableSorts targets by accumulated threat; supports custom weights and decay.
Boss barShows mob health to players within range; configurable color and style.

Default runtime folder ​

text
plugins/EmakiMobs/
├── config.yml
├── target_selectors.yml    ← target selectors and score snapshots (static file, released only when missing)
├── mobs/                   ← mob definition files
├── loot_tables/            ← loot table files
├── spawn_rules/            ← spawn rule files
└── lang/

mobs/ defines mobs, loot_tables/ defines drops, and spawn_rules/ defines when and where mobs appear. Any .yml file placed in these directories takes effect after /emakimobs reload.

target_selectors.yml is referenced by a mob definition's target_selector field. It is a static file (never merged or overwritten by a version upgrade) and is released from the jar only when missing. See the "Target selectors" section of Definitions for its fields.

Shipped defaults (EmakiMobs/src/main/resources/config.yml, excerpt):

yaml
version: "1.0.3"
language: "zh_CN"
release_default_data: true

model:
  api: "auto"
  view_distance: 48.0
  lod:
    near: 16.0
    mid: 32.0
    far: 48.0
  movement_check_interval_ticks: 5
  death_detach_delay_ticks: 40
  walk_speed_threshold: 0.12
  run_speed_threshold: 0.28
  transitions:
    idle_fade_ticks: 5
    walk_fade_ticks: 5
    run_fade_ticks: 5
    death_fade_ticks: 0
    hurt_fade_ticks: 2
    attack_fade_ticks: 3
    skill_fade_ticks: 3
    interact_fade_ticks: 3

Force BetterModel and tighten the mid tier to 24 blocks:

yaml
language: "en_US"

model:
  api: "better_model"
  lod:
    near: 12.0
    mid: 24.0
    far: 48.0

Typical workflow ​

  1. Create a mob definition in mobs/ with an id, entity type, and component values.
  2. Create a matching loot table in loot_tables/ with a mob_id matching the mob id.
  3. Add a loot_table key to the definition's components to enable that YAML loot table (only the key's presence matters; see the "Loot fields" section of Components).
  4. Add a spawn rule in spawn_rules/ to link the mob to spawn conditions.
  5. Run /emakimobs reload or restart the server.
  6. Use /emakimobs spawn <mob_id> to test the mob at your current location.
