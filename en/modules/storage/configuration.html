Configuration ​

config.yml keys are covered one by one. EmakiStorage's configuration is split across three files, and the capacity domain model has a page of its own:

TopicPage
The gui/storage_gui.yml template plus the gui and display sectionsGUI and Display

After you edit, run /estorage reload to reload config, language and GUI templates

yaml

op_bypass: true

Keep the two empty cases apart: when deposit_filter.mode is whitelist with both entries and matcher empty, nothing can be deposited; when it is blacklist with both empty the filter is effectively off and everything passes. The unique-marker test is structural: it checks whether the item's own PersistentDataContainer is non-empty rather than reading its display name or lore

Note: withdraw_amounts only accepts non-negative values. A negative value is parsed as 0, which turns that click kind into a no-op rather than falling back to the default amount

These keys decide the amount each click moves and whether it is allowed at all; the full click semantics table, the rejected click kinds and the search-mode restriction live in GUI and Display

Here is another example: take one unit per right-click, disable the middle-click custom amount, and allow one entry to span several slots

yaml
behavior:
  withdraw_amounts:
    left: 64
    right: 1
    shift_left: 2304
    shift_right: 576
  withdraw_prompt:
    enabled: false
  multi_slot_stacking: true

These two keys are shared by two interactions: search.input.timeout and search.input.cancel_keywords both serve the search prompt and the middle-click custom withdrawal amount chat input. So if you shorten the timeout to 5, both inputs get the shorter wait

While a search filter is active the display area cannot accept deposits; right-clicking the search button while searching clears the filter

For example, use English cancel keywords and force chat input

yaml
search:
  operators:
    name: "n:"
    lore: "l:"
  input:
    mode: "chat"
    timeout: 15
    cancel_keywords: ["cancel", "quit"]

Dialog Configuration Block ​

behavior.withdraw_prompt.dialog and search.input.dialog use exactly the same key set as the EmakiCoreLib dialog definition files (EmakiCoreLib/dialogs/*.yml), including type, external_title, after_action, columns, exit_button, plus per-input width, initial and label_visible. The only difference is that the id is supplied by the plugin and must not be written in the configuration

How the text resolves: the title, the text of body entries, input labels and button label / tooltip are resolved as language keys first. When you write a key such as dialog.withdraw.title it is read from lang/*.yml, and a missing key renders literally, so MiniMessage text can be written directly instead. The search dialog body supports the four operator placeholders %name%, %lore%, %id% and %exclude%

Prerequisites first: dialogs require client 1.21.6 or newer and EmakiCoreLib's dialog.enabled set to true. If inputs lacks the key the feature needs (amount for withdrawal, query for search) or carries no buttons, the dialog is treated as unavailable: mode: auto falls back to chat input, while mode: dialog disables the interaction and reports dialog.unavailable

You can also change the operator prefixes so they avoid clashing with item names. Search syntax:

  • Whitespace separates terms and every term must match (AND)
  • A term may carry one scope prefix and one exclusion prefix in either order, so !@diamond and @!diamond are equivalent
  • Without a scope prefix a term matches the combined text, which is built from display name plus lore plus identifier, so an unscoped search can also hit a material key
  • All matching is substring matching against text that was already lower-cased and stripped of formatting

Note: no regular-expression search is provided, not even behind an admin flag. A hostile pattern can stall the server through catastrophic backtracking, and substring matching covers the actual use case

auto_pickup ​

yaml
auto_pickup:
  enabled: true
  mode: on_pickup
  radius: 8
  max_radius: 16
  scan_interval_ticks: 10
  default_enabled: false
  notify_cooldown_ms: 3000
FieldTypeRequiredDefaultAccepted valuesDescription
enabledbooleanNotruetrue / falseMaster switch for auto-pickup. Once off the feature is entirely unavailable, /estorage autopickup is refused and the scan task never starts
modeenumNoon_pickupon_pickup (alias pickup) / radius (alias range)Working mode: on_pickup only collects when the vanilla pickup event fires (no extra cost); radius additionally starts a scheduled scan that collects every dropped item within the configured radius (stronger, but it costs performance). An unknown value falls back to on_pickup
radiusintNo8Clamped to 1–max_radiusradius mode only. Scan radius in blocks, server-wide. Ignored in on_pickup mode
max_radiusintNo16≥ 1 (values below 1 are treated as 1)radius mode only. Clamp ceiling for radius. max_radius is resolved first and then clamps radius, so lowering it tightens radius immediately
scan_interval_ticksintNo10≥ 1 (values below 1 are treated as 1)radius mode only. Server-wide scan interval in ticks. 20 ticks = 1 second, so 10 scans twice per second. Lower reacts faster but costs more CPU. Ignored in on_pickup mode
default_enabledbooleanNofalsetrue / falseDefault per-player switch state when a player's data is first loaded. true means on by default and players turn it off with /estorage autopickup off; false means off by default. A switch already written to disk is never overwritten by this key
notify_cooldown_mslongNo3000≥ 0 (negatives are treated as 0)Notification cooldown for refused pickups, in milliseconds. Further refusals inside the cooldown send no message, avoiding chat spam; 0 notifies every time

Players manage their personal switch with /estorage autopickup (requires emakistorage.autopickup, default true). There is no per-player radius: radius is a single server-wide value you can only change in the configuration

Watch the cost: mode: radius scans every online player every scan_interval_ticks, so with 100 players online and scan_interval_ticks: 20 that is five all-player scans per second. Tune the interval to the server, or use on_pickup mode

For example, switch to radius scanning and sweep 6 blocks every 2 seconds

yaml
auto_pickup:
  mode: "radius"
  radius: 6
  max_radius: 16
  scan_interval_ticks: 40

persistence ​

yaml
persistence:
  autosave_interval_seconds: 300
  drain_timeout_seconds: 10
FieldTypeRequiredDefaultAccepted valuesDescription
autosave_interval_secondslongNo300≥ 0 (negatives are treated as 0)Autosave interval in seconds. 0 disables the timer, leaving saves to GUI close and logout. The legacy key name autosave_interval is still accepted and is migrated automatically at startup
drain_timeout_secondslongNo10≥ 1 (values below 1 are treated as 1)Seconds to wait for file writes to drain when the plugin disables. The legacy key name drain_timeout is still accepted and is migrated automatically at startup

You will see multiple amount changes within one interval merge into a single write. Every save is a full rewrite of storage.dat: write a sibling .tmp, re-read and validate the record count, then replace atomically. A failed write leaves the previous file untouched and deletes the tmp

For example, save every 10 minutes and allow up to 30 seconds on shutdown

yaml
persistence:
  autosave_interval_seconds: 600
  drain_timeout_seconds: 30

logging ​

yaml
logging:
  enabled: true
  retention_days: 30
  sources: []
FieldTypeRequiredDefaultAccepted valuesDescription
enabledbooleanNotruetrue / falseWhether ordinary flow records are written. It has no effect on the always-recorded admin operations
retention_daysintNo30≥ 0 (negatives are treated as 0)Log retention in days. <= 0 disables purging
sourceslist<string>No[]gui / command / api / action / auto_pickup; an empty list means allRecord only these surfaces, matched exactly by source id. The shipped config.yml comment lists only the first four; the fifth source auto_pickup (auto-pickup deposits) also exists

The log layout is one directory per player and one file per day: logs/<uuid>/<yyyy-MM-dd>.log. Expired files are deleted per day; once every file for a player has expired, their directory is removed as well. Purging runs during reload and shutdown

Remember: the three admin operation kinds ADMIN_SET, ADMIN_GIVE and ADMIN_CLEAR are always recorded, ignoring both enabled and sources. An admin disabling logging to save disk is no reason to lose the audit trail of admin changes

The flow log is write-only: business logic never reads these files, which removes the need for an index, compaction, schema versioning or cross-file transactions. A failed write only logs a warning and never fails the storage transaction that produced it. Records queued for the same player are flushed as one append, so your 36-slot bulk deposit produces one file operation rather than 36

For example, keep 7 days and record only what players do directly in the window

yaml
logging:
  enabled: true
  retention_days: 7
  sources: ["gui"]
