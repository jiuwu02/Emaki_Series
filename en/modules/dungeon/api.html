API ​

Third-party plugins talk to EmakiDungeon through emaki-dungeon-api (current version 1.0.3). The API jar is a compile-time dependency only; the matching runtime artifact is EmakiDungeon-1.0.13.jar

Maven coordinates ​

xml
<repositories>
  <repository>
    <id>jiuwu-releases</id>
    <url>https://repo2.crypticlib.com/releases/</url>
  </repository>
</repositories>

<dependency>
  <groupId>emaki.jiuwu.craft</groupId>
  <artifactId>emaki-dungeon-api</artifactId>
  <version>1.0.3</version>
  <scope>provided</scope>
</dependency>
kotlin
repositories { maven("https://repo2.crypticlib.com/releases/") }
dependencies { compileOnly("emaki.jiuwu.craft:emaki-dungeon-api:1.0.3") }

Compile-time only

The runtime embeds the unrelocated API classes. Do not install, bundle, shade, or relocate the API jar; duplicate ClassLoader types break events and the bridge

The EmakiDungeonApi facade ​

Everything starts at the static facade emaki.jiuwu.craft.dungeon.api.EmakiDungeonApi with five domain facades, and accessors never return null:

java
// availability and identity metadata; notInstalled while EmakiDungeon is absent
var status = EmakiDungeonApi.status();

var dungeons = EmakiDungeonApi.dungeonApi();   // entry and instance queries
var party    = EmakiDungeonApi.partyApi();     // party
var instance = EmakiDungeonApi.instanceApi();  // force stop
var script   = EmakiDungeonApi.scriptApi();    // flow scripts and triggers
var editor   = EmakiDungeonApi.editorApi();    // open the editor
  • install / uninstall and the Bridge interface are internal and non-extendable; never call or implement them
  • Resolve accessors at the point of use, never cache them in a field: reload swaps the backing bridge
  • With the plugin absent every facade returns a no-op implementation answering Result.err(ErrorCodes.NOT_INSTALLED, ...); use status().usable() to check whether the bridge is live

MethodReturnsDescription

Result<T> and error codes ​

Every fallible method returns the Result<T> record composed of code / messageKey / args / value:

java
Result<PartyId> result = EmakiDungeonApi.partyApi().create(player.getUniqueId());
if (result.isSuccess()) {
    PartyId id = result.value();   // value() is null on failure
} else {
    // result.code() is a stable error code, result.messageKey() maps into your own lang files
}

Events ​

Public events live in emaki.jiuwu.craft.dungeon.api.event. The DungeonEvent base carries getInstanceId() and getDungeonId(); DungeonChallengeStartEvent and DungeonChallengeCancelEvent carry only dungeonId (no instance exists yet at that point)

java
@EventHandler
public void onDungeonComplete(DungeonCompleteEvent event) {
    // event.getInstanceId() / getDungeonId() come from the base class
    log(event.getDungeonId() + " cleared: " + event.getScore() + " points in "
        + event.getDurationMs() + "ms");
}
  • All events except the two marked "Yes" have no cancellation channel and are informational only
  • The two cancellable events are dispatched before the plugin proceeds: cancelling changes what the plugin does next, which makes them suitable for custom gating beyond permissions

Threading and lifecycle ​

  • Before touching player inventories, worlds, or entities, make sure you are on the owner thread required by Bukkit/Paper; when you cannot confirm it, schedule back to the main thread (the corresponding region thread on Folia)
  • When EmakiDungeon is absent, first loading the API classes carries a linkage-failure risk; isolate such calls and catch LinkageError | RuntimeException
  • Events are dispatched synchronously at internal flow points; do not block inside a listener and do not mutate dungeon world state there without considering flow progression
