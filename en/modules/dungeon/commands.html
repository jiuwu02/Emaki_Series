Commands ​

The main command is /edungeon; the short alias is /ed. Player-side commands are open by default (emakidungeon.play defaults to true), while admin and editor commands require their own permissions

Player commands ​

CommandDescriptionPermission
/edungeon helpShow command help (same as running /edungeon with no arguments)emakidungeon.play
/edungeon listList the currently available dungeonsemakidungeon.play
/edungeon enter <dungeonId>Start a challenge and enter the dungeon; in a party only the leader may startemakidungeon.play + emakidungeon.dungeon.<dungeonId>
/edungeon leaveLeave the current dungeon; asks for a second confirmation first - type confirm in chat to leave, cancel to stayemakidungeon.play
/edungeon cancelCancel an ongoing entry wait or challenge (any member can cancel during the ready window)emakidungeon.play
/edungeon readyConfirm readiness during the ready window (the confirmation button works too)emakidungeon.play
/edungeon rewardsOpen your personal reward box and claim payoutsemakidungeon.play
/edungeon stats [player] [dungeonId]Show entry counts (day/week/month and cooldown) plus best resultsemakidungeon.play
/edungeon rank <dungeonId>Show the dungeon's top 10 leaderboard (score, duration, difficulty, party)emakidungeon.play
/edungeon globalchat <on|off>Toggle global chat listening; on bridges chat in and out of the instance, off keeps dungeon chat inside the instanceemakidungeon.play
/edungeon editor <dungeonId>Open the map editor and enter the dungeon's dedicated edit worldemakidungeon.editor
/edungeon recruit <open|close|list|join>Party recruit board: open <dungeonId> [difficulty] publish a recruit (leader only), close close it, list list open recruits, join <number> join oneemakidungeon.play
/edungeon match <join|leave>Local auto-match: join <dungeonId> [difficulty] enter the match queue, leave leave the queueemakidungeon.play
/edungeon spectate <next|prev>Switch the spectate target while spectating (next / previous); warns when you are not spectatingemakidungeon.play

The recruit board and auto-match are controlled by the global matchmaking section (both report "disabled" when it is off), and recruits expire after matchmaking.recruit-ttl-seconds; after a match succeeds the leader starts the run with /edungeon enter <dungeonId>

Party subcommands ​

/edungeon party <sub> manages your party:

SubcommandDescriptionRestrictions
createCreate a new party (you become the leader)Cannot create while already in a party
invite <player>In a party: invite that player (leader only); not in a party: ask to join, handled by the invite modeLeader-only when you already have a party
acceptThe invitee accepts an invitation; the receiver of an application (the leader) approves itDepends on whether you received an invite or an application
denyRefuse a received invite (invitee) or reject an incoming application (leader)Depends on whether you received an invite or an application
kick <player>Remove a memberLeader only
leaveLeave the party (the leader hands over to another member first)—
disbandDisband the whole partyLeader only
chatToggle the party channel: once on, your messages are visible to party members only—

The invite mode comes from the global party.invite-mode and decides what happens when a player without a party asks to join another: public joins directly, apply files an application waiting for the leader's approval, invite only lets invited players in (any other value behaves like invite). The party size cap is party.max-size

Random dungeon commands ​

Dungeons with type: random use the random-generation gameplay; operate them with /edungeon random <sub>:

SubcommandDescriptionPermission
create <dungeonId> [players] [seed]Create a random dungeon instance for the dungeon from the random-generation config; the player count affects the room count, and an empty seed is picked at random; available only for dungeons with type: random, other types are refused outrightemakidungeon.play
enter <instanceId>Enter a created random dungeon instanceemakidungeon.play
leaveLeave the current random dungeon instanceemakidungeon.play
listList running random dungeon instances (instance id, state, room count, seed)emakidungeon.play
recordsList instance records (record ids can be used with replay)emakidungeon.play
stop <instanceId>Force-stop a random dungeon instanceemakidungeon.admin
replay <recordId>Re-derive the layout from an instance record for replay verificationemakidungeon.admin
reloadReload random-dungeon.yml and the structure templates of all dungeonsemakidungeon.admin

The structure templates (rooms / corridors) of a random dungeon come from the editor's region collection feature and are stored under plugins/EmakiDungeon/world/<dungeonId>/structures/; the collection flow is covered under the editor session commands below, and the generation parameters on the Configuration page

Editor session commands ​

Run /edungeon editor <dungeonId> with the emakidungeon.editor permission to open an editing session:

SubcommandDescription
menuOpen the editing main panel; in a type: random dungeon it instead opens the region collection GUI
pos1 / pos2Record the first / second corner of a region (stand on each diagonal corner of the target area); in a type: random dungeon they frame the structure region to collect
anchor add <id> <facing> <w> <h>Register a door point at the crosshair landing spot (within 12 blocks): the facing is n / e / s / w, and width and height are the door opening size (1–16); the region must be framed first, available only for type: random dungeons
anchor remove <id>Remove a door point; available only for type: random dungeons
statusShow the current region collection session (structure type, tags, door point count, point count, floor); available only for type: random dungeons
mark <type> [id]Place a marker on the block you are looking at (16 blocks reach); markers are staged in the session and written to flow.yml on save
marksList the markers staged in this session
saveWrite the staged markers and panel edits back to the template file and save the terrain (same as "Save and write back" in the panel)
fill <block>Fill the area circled by pos1 + pos2 (written in frames, with a size cap)
testTest start: runs the normal entry flow, counts nothing and never ranks; refused while unsaved changes exist
exitLeave the session; refused while unsaved changes exist, so save or discard first

anchor and status report "random type only" in dungeons of other types; menu / pos1 / pos2 branch their semantics by dungeon type

Markers come in three coordinate flavors, 21 module types in total (one per flow.yml module):

TypeHowPurpose
entryPointEntry location (one per dungeon; duplicates are refused)
roomRegionRoom
checkpointRegionCheckpoint
respawnPointRespawn point
exitPointExit
gateRegionGate door area
spawnPointSpawn point
triggerRegionTrigger zone
blockPointBlock interaction
chestPointReward point
optionPointOption node
tipPointTip point
teleportRegionTeleport zone
boundaryRegionBoundary zone
effectRegionEffect zone
mechanismRegionMechanism
room_timerRegionRoom timer
kill_targetNo coordinatesKill target
itemPointItem interaction
fxPointEffect point
temp_itemNo coordinatesTemporary item

How they work: point markers go on the block you are looking at; region markers need pos1 + pos2 corners (with no corner recorded yet, the first mark records the looked-at point as pos1); no-coordinate markers record config only. The configurable fields of each type are documented on Flow & Triggers. Boss is not a separate marker: mob entries in the waves of a spawn point are marked with boss: true

The main editor panels (metadata, spawn points and waves, gates, branch options) are edited through GUIs. Markers and panel edits are only staged; nothing reaches the template files until you click "Save and write back" (or run save), and exiting without saving discards everything.

In a type: random dungeon, right-clicking with an empty hand opens the region collection GUI (metadata and tags, door points, module points, selection, create-region panels and more): "Create region" on the main panel offers room / corridor, and the selection framed by the current pos1 / pos2 is written to world/<dungeonId>/structures/ with the id auto-numbered as room_N / corridor_N; after the write the session automatically resets to a new region, so the next pos1 / pos2 frame collects the next structure

Only one editing session per dungeon template is allowed at a time

Admin commands ​

/edungeon admin <sub> requires emakidungeon.admin (default OP):

SubcommandDescription
instancesList running instances (id, dungeon, state, party, write-queue backlog)
inspect <instanceId>Show instance details: difficulty, drop mode, type, test flag, party, elapsed time, and the flow timeline
stop <instanceId>Force-stop a specific instance
statusOverview: instance count, live virtual threads, template count, per-pool usage, and write queues
reloadReload the main configuration and all dungeon configs; running instances are untouched, only newly created instances pick up changes
validateValidate every dungeon template and report missing flow.yml or invalid configurations
poolreset <dungeonId>Force-reset the pool spare world of a dungeon
clearslotsClear leftover pool slot reservations

NOTE

admin subcommands are dispatched before the player check, and reload has no player-only restriction: the console can run /edungeon admin reload directly, and so can bots and scripts. Players need emakidungeon.admin; the console holds every permission by default

Permission nodes ​

NodeDefaultPurpose
emakidungeon.playAll playersEntering, party, stats, and global listening player commands
emakidungeon.dungeon.*All playersEntry to all dungeons (actually checked per emakidungeon.dungeon.<dungeonId>)
emakidungeon.bypass.limitOPBypass entry counts and cooldowns
emakidungeon.bypass.escapeOPEscape-protection exemption (debugging and maintenance)
emakidungeon.scriptOPDungeon script loading and trigger registration
emakidungeon.editorOPMap editor sessions
emakidungeon.adminOPInstance management, force stop, reload, pool maintenance
emakidungeon.*OPWildcard covering everything above

emakidungeon.dungeon.<dungeonId> is dynamically registered on startup and reload for every dungeon folder under world/, and defaults to open for all players; deleting the dungeon removes the node. For a members-only dungeon, turn the default off in your permission plugin and grant the node to the right groups

Command rules inside a dungeon ​

Commands run by players inside an instance pass two gates:

  1. Escape blacklist (escape.blacklist, supports * wildcards): a hit is refused immediately with "command restricted in this dungeon (escape blacklist)", and no allow-rule can override this layer
  2. Command guard (commands.mode, blacklist or whitelist): evaluated against the global commands.rules and the dungeon-level commands.allow, refusing with "command restricted in this dungeon (command guard)"

Configuration details are on the Configuration page
