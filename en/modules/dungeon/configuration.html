Configuration ​

EmakiDungeon ships three configuration files: the global plugins/EmakiDungeon/config.yml, the per-dungeon plugins/EmakiDungeon/world/<dungeonId>/config.yml, and the reward box GUI plugins/EmakiDungeon/gui/rewardbox.yml. After you edit them, run /edg admin reload (this command is run by a player with emakidungeon.admin); running instances are unaffected, only newly created instances pick the changes up

The top-level version and language fields are maintained by the resource sync process — do not edit them by hand. Per-dungeon configs have no schema compatibility layer and are validated strictly at load time. The "Range" column below marks keys with source-level validation; keys showing — are not range-checked by the code, and invalid values are handled in one of two ways:

  • Load error (the dungeon is skipped, console reports an invalid dungeon configuration): pool.max-worlds, enter.prepare-window-seconds, enter.wait-timeout-seconds, enter.wait-channel, the limits.daily.time-window format, and days/weeks entries under limits
  • Silent fallback: the plugin drops invalid entries, clamps them to a boundary, or replaces them with the default (see each row)

storage / folia / action ​

KeyTypeDefaultRangeDescription
storage.bstatsstringdisableddisabled only for nowbStats is not wired up this phase; it will be integrated through CoreLib once the interface lands
folia.held-worlds-maxint10—Global cap on suspended worlds on Folia; at capacity new challenges are refused as full and the state resets on restart
action.<segmentId>map{}Action pipeline linesDungeon lifecycle actions; the segment id is the key and the value is a CoreLib action pipeline

The action section supports 11 segment ids: dungeon_enter, dungeon_exit, dungeon_room_clear, dungeon_gate_open, dungeon_wave_start, dungeon_score, dungeon_complete, dungeon_fail, dungeon_reward, dungeon_ending, dungeon_destroy. You write them with the same syntax as the CoreLib actions, for example:

yaml
action:
  dungeon_enter:
    - 'self | send_message text="<green>进入副本</green>"'

Per-dungeon world/<dungeonId>/config.yml ​

When this file is missing, the plugin generates it from the bundled template at startup or reload; existing files are never overwritten

limits entry limits ​

The evaluation order is fixed as month > week > day: if any tier is unsatisfied or exhausted, entry is refused and lower tiers are not evaluated. count: 0 means unlimited for that tier, and negative values are treated as 0

KeyTypeDefaultRangeDescription
limits.daily.countint1>= 0Entries per day; 0 is unlimited
limits.daily.time-windowstring"""HH:mm-HH:mm" or emptyDaily challenge window; may cross midnight (for example "23:00-01:00"); a malformed value fails dungeon loading
limits.weekly.countint0>= 0Entries per week
limits.weekly.dayslist<int>[]1–7 (1 = Monday)Allowed weekdays; empty list does not restrict; a bad entry fails dungeon loading
limits.monthly.countint0>= 0Entries per month
limits.monthly.weekslist<int>[]1–6Allowed week-of-month (Monday-based); empty list does not restrict; a bad entry fails dungeon loading
limits.cooldown-secondsint0>= 0Cooldown between entries; negatives become 0

Reward box GUI gui/rewardbox.yml ​

The layout of this GUI is fixed and not configurable; only two numbers are exposed:

KeyTypeDefaultRangeDescription
default-pagesint1—Base visible pages for players without a higher page permission
capacity-slotsint135—Total reward box capacity in slots; reaching it means the box is full - see Challenges & Rewards for the full rules

Flow file world/<dungeonId>/flow.yml ​

This file holds every flow module (rooms, waves, gates, options) and is generated when missing. See Flow & Triggers for the full structure
