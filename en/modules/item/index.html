EmakiItem ​

EmakiItem provides lightweight custom items, stable item IDs (the unique ID you assign each item in config), sets, trigger actions, auto update, and PlaceholderAPI support, and the sections below show which page covers each feature, what config.yml exposes, and how it works with other modules. Treat it as the starting point for equipment progression: create one item with a stable ID first, then hand it to Forge, Strengthen, Gem, Attribute, and Skills to keep building on it

You write items into items/ and sets into sets/; gui/ holds the repair and two browser templates (repair_gui.yml, pack_browser_gui.yml, item_browser_gui.yml), and id_aliases.yml stores renamed item ID mappings

Every subdirectory of items/ is an item pack; drop a pack.yml in it to define how that pack looks in the browser, see Browser GUI

Main configuration ​

Before reading the tables, keep two points in mind. config.yml holds only global settings; each item's own behavior lives in its definition file. "Required" asks whether the plugin falls back on its own when a key is missing: every key below has a fallback, so all read "No". "Range" states the constraint the plugin actually enforces; "—" means the plugin performs no validation

Top-level settings ​

FieldTypeRequiredDefaultRangeDescription
versionstringNo"3.0.0"—Config structure marker maintained by the project's resource sync flow, not a feature switch. Falls back to 2.6.7 when absent
languagestringNozh_CN—Language file name, matching lang/<language>.yml. Falls back to zh_CN when absent
release_default_databooleanNotruetrue / falseWhether bundled default data such as items/ and sets/ is released at startup; when disabled only existing data is loaded and no missing sample is generated. This does not control config.yml or language files
yaml
# Shipped defaults
version: "3.0.0"
language: "zh_CN"
release_default_data: true

Usage example: switch to English and stop releasing sample data

yaml
language: "en_US"
release_default_data: false

Usage example: declare a kill counter with thresholds and migrate a legacy field by schema version

yaml
item_state:
  fields:
    kills:
      type: INTEGER
      default: 0
      min: 0
      max: 9999
      thresholds:
        novice:
          value: 10
          once: true
          message_key: "state.kills.novice"
          sound: "minecraft:entity.player.levelup"
          sound_volume: 1.0
          sound_pitch: 1.2
        veteran:
          value: 100
          actions:
            - 'send_message text="<gold>Kill streak reached.</gold>"'
  migrations:
    "1":
      from: 0
      to: 1
      rename:
        kill_count: kills
      retype:
        kills: LONG
      drop:
        - legacy_tag

Interactions ​

Keep the split in mind: set_bonus.refresh_triggers controls set state refreshing, while item auto-update is controlled separately by update.triggers in an item definition; neither overrides the other

item_state.* applies to the emaki:item_state PDC partition (plugin-defined data, the hidden fields a plugin writes onto an item) and is read and written by the item_state_* action stages and the API. The whole section is additive: leave every key untouched and the behavior matches the previous version. proficiency_guard.* applies to slot dispatch for damage_dealt, kill_entity, and kill_player; everything except dedupe_per_event defaults to disabled or unlimited

Typical item lifecycle ​

  1. You define item IDs, material, name, lore, and components in items/
  2. Add Attribute stats, Skills, or set info when you need them
  3. Give the item out with a command
  4. A player equips or uses the item
  5. Item refreshes the item automatically at each trigger
  6. Forge / Strengthen / Gem then keep writing their own layers on top
  7. CoreLib rebuilds the final display
